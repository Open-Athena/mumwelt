# Bringing the 67B-A2B up on H100s

## Bottom line

The 67B-A2B production shape — the d2560 "Grug" MoE, **67,078,882,816 params total / ~2.01B active per token, 26 layers, 256 experts top-4** ([#6367](https://github.com/marin-community/marin/issues/6367), [#6044](https://github.com/marin-community/marin/issues/6044)) — **never launched its 10T-token production run on CoreWeave's H100s.** After roughly three weeks stalled behind a first-step memory wall and Muon's poor fit under FSDP, the run was **handed off to TPU**: v4-1024 on the morning of June 24, then the full v4-2048 by June 27 ([summary 2026-06-22_2026-06-28](https://mws.oa.dev/summaries/summary-2026-06-22_2026-06-28.html), [#6044 c/4792727390](https://github.com/marin-community/marin/issues/6044#issuecomment-4792727390)).

The honest headline on MFU: the best *measured* end-to-end numbers for the real 26-layer d2560 shape on H100 were **~20–21% final-step / ~15% mean, at 2–4 nodes (16–32 H100)** — and the program's own stated bar, **">20 MFU at 128 GPUs," was never measured at all**. It remained an open target when the run left for TPU.

An important correction to the folklore: it is **not** true that nothing ever trained. Full-depth d2560 runs did train on H100 at reduced batch. What never cleared was the **B256 / seq4096** production batch gate — and no H100 run ever used the production **seq8192**.

## What we tried

### 1. The first-step memory wall — partially solved, never fully

Every **B256 / seq4096** full-depth attempt died before step 0 at `jax.block_until_ready(metrics["train/loss"])` with `RESOURCE_EXHAUSTED`, on H100 80GB ([#6367](https://github.com/marin-community/marin/issues/6367)):

- GM2560-MFU-004 (32 nodes, EP8): "failed before step 0 with `RESOURCE_EXHAUSTED: Out of memory while trying to allocate 60.91GiB`"
- MAY-030 (B256, `remat=recompute_all`): "`Out of memory while trying to allocate 72.03GiB`… remat alone is not enough"
- MAY-055 (B8/N4): "still OOMed… at `132.44GiB`, essentially the same as the `133.39GiB` failure, so smaller real batch is not the main lever"

**Diagnosis** ([c/4710624468](https://github.com/marin-community/marin/issues/6367#issuecomment-4710624468)): the culprit was a global logits-like buffer in the loss/output/vocab SPMD path, not the optimizer — "`B16 * S1024 * V128256 * fp32` is 7.83 GiB, and 8x that is 62.6 GiB, close to the observed 63.7-63.8 GiB… a global logits-like/loss-output buffer being replicated or kept live through SPMD/lowering."

**Tried and failed:** the AdamH hyperball-materialization theory. [PR #6385](https://github.com/marin-community/marin/pull/6385) computed the update algebraically instead of materializing the full post-step parameter; the A/B moved 63.80 GiB → 63.69 GiB. dlwh's close-out: **"no evidence this helps so closing."**

**What actually worked:**
- **Reducing batch while preserving `data=16` sharding.** MAY-042 (B128, seq4096, 16 nodes) **completed 6/6 steps with `loss=11.3`** and produced the first usable full-seq4096 profile — "reducing batch was the right move, but preserving `data=16` was the key" ([c/4706090648](https://github.com/marin-community/marin/issues/6367#issuecomment-4706090648)). Note the author explicitly declined to claim MFU from it.
- **Dropping sequence length.** "B256 full-depth succeeds at seq2048" (MAY-031).
- **B-tiled fused cross-entropy** ([PR #6572](https://github.com/marin-community/marin/pull/6572), follow-up [#6596](https://github.com/marin-community/marin/issues/6596)) bounded logit memory at exactly the d2560 shape: XLA reference 25.02 GiB grad module → 5.05 GiB at B-tile 4096, at ~16% combined-throughput cost. *Caveat: no comment in the corpus states this fixed the d2560 first-step OOM — the link is circumstantial.*

A large fraction of at-scale failures were **not memory at all** but `Initialize clique: devices=128/256` rendezvous stalls (MFU-006/007, MAY-034), which died with no W&B history.

### 2. Muon under FSDP — shelved

Muon was the single biggest tax. The clean A/B on one 8×H100 node ([#6493 c/4757823407](https://github.com/marin-community/marin/issues/6493#issuecomment-4757823407)): **May140 MuonH at 4.75 MFU / 1.492 s/step vs May141 SGD at 16.19 MFU / 0.4378 s/step** — "roughly 1.05s/step of the May140 profile [attributed] to Muon/update overhead."

What was tried in #6493: batched Newton-Schulz grouping (the path was running NS "one matrix at a time"); a **cap-256 vs cap-512** sweep — cap256 won decisively (h1: 17.886 ms vs 34.028 ms), "the flat `[512, ...]` batched GEMM shape is slower than two `[256, ...]` batches"; and a **4D `[group, expert, m, n]` layout**, the one clear win (h1 at data=2/expert=4: 34.725 ms → **14.367 ms**).

But the math was never the bottleneck. Close-out reading ([c/4752816120](https://github.com/marin-community/marin/issues/6493#issuecomment-4752816120)): **"the grouped MuonH math itself is already good; the expensive part is still grouped-update → FSDP apply"** (~0.62 s boundary-only on 4 nodes). The objective audit was blunter ([c/4756630388](https://github.com/marin-community/marin/issues/6493#issuecomment-4756630388)): "Avoiding the compiled collective explosion: **not achieved.** Direct target-layout reshard, tuple-returning `shard_map`, custom partitioning, packed bridges, ppermute bridges, and grouped-trace restore/apply all still compile into grouped-to-FSDP all-gathers or worse."

**Verdict, June 26 OA meeting** ([Discord](https://discord.com/channels/1354881461060243556/1399998407657001062/1520200189690773564)):
> "We're currently at ~19.9 MFU on 4 nodes w/ SGD/Adam. Some low hanging fruit remains. **Muon needs to go for now. 10% step-count improvement isn't worth atm. We'll need much faster interconnect or PP.**"

### 3. Pipeline parallelism — never beat FSDP on H100

Russell Power's zero-bubble/1F1B prototype ([#6532](https://github.com/marin-community/marin/issues/6532), [PR #6534](https://github.com/marin-community/marin/pull/6534)) was gradient-exact to ~1e-7 and bit-identical in loss. It was also consistently slower on H100:

| Config (8×H100, M=8, fwd+bwd) | s/step | tok/s |
|---|---|---|
| FSDP | 1.01 | 65k |
| 1f1b (3F) | 2.20 | 29.8k |
| zb (5F) | 2.43 | 27.0k |

On 2 nodes / 16×H100 with the best transport (`ppermute` + local-accum reduce), PP still ran **4.01 s/step vs FSDP's 1.53 s — 2.62× slower** ([c/4794551548](https://github.com/marin-community/marin/issues/6532#issuecomment-4794551548)). An early "98% Python dispatch" diagnosis was **retracted by its own author**; the fitted result was structural — PP marginal cost ~50 ms/batch-unit vs FSDP's ~6 ms, batch-invariant ([c/4795281113](https://github.com/marin-community/marin/issues/6532#issuecomment-4795281113)).

Two things PP genuinely won: **memory** (an 8M-token batch in 22.8 GiB under 1F1B where FSDP OOM'd at 1M tokens / ~137 GiB of unchunked logits) and **Muon amortization** (+0.09 s tax vs FSDP's +0.76 s single-node). Neither was enough. Parked June 25; the one place PP beat FSDP was **TPU v6e-32 at 1.22×**, not H100 ([#6534 c/4773325024](https://github.com/marin-community/marin/pull/6534#issuecomment-4773325024)).

### 4. DeepEP — dead end on CoreWeave

DeepEP internode dispatch got as far as passing backward smokes on 2 nodes ([#4312 c/4762462368](https://github.com/marin-community/marin/issues/4312#issuecomment-4762462368)) but **never produced a training-throughput row**. Both the JAX FFI wrapper and upstream's native path reached `notify_dispatch` and timed out, root-caused to NVSHMEM/IBGDA transport init failing on CoreWeave. Ring EP stayed the fastest available primitive throughout, and [#6597](https://github.com/marin-community/marin/issues/6597) was launched days later explicitly as the DeepEP-free alternative ("Keep DeepEP out of this path; it is a baseline only").

### 5. The forward bet after Muon and PP: Pallas kernels + fp8

**fp8 is where the clean measured wins are.** [PR #6660](https://github.com/marin-community/marin/pull/6660) found that the legacy quantize-dequantize recipe meant "**On Hopper the forward GEMM silently falls back to bf16**"; the direct op emits genuine `f8e4m3`. [PR #6880](https://github.com/marin-community/marin/pull/6880) delivered "**~1.41× fwd+bwd speedup**" on the MoE expert MLP. The over-the-wire spike sealed at **"bf16 33.47 ms/step versus FP8 23.28 ms/step, or 1.438×"** on 2-node H100 EP16 over IB ([#6911](https://github.com/marin-community/marin/issues/6911)). Load-bearing caveat: "**scientific validation is still required before any training run — default stays bf16**" (dx relative Frobenius error ~1e-1).

**The Pallas/Mosaic fused MoE kernel partly worked.** At exact target shape it hit **2.09× vs `ragged_all_to_all`** forward ([c/4826981254](https://github.com/marin-community/marin/issues/6597#issuecomment-4826981254)) — but the win is forward-only and shape-specific (at a tiny shape it was ~12× *slower*), the backward remains reference-heavy JAX, and the 250 TFLOP/s aggregate fwd+bwd goal was **not reached**.

## The final MFUs

All rows below are the **real 26-layer d2560 / 67B-A2B shape on CoreWeave H100** (`cw-us-east-02a`), ring MoE, SGD fwd/bwd, FA4, Pallas CE, bf16, `model_axis=1`, `expert_axis=8`, B4/device + `recompute_all`, synthetic data — from [#4312 c/4796604837](https://github.com/marin-community/marin/issues/4312#issuecomment-4796604837), reported 2026-06-25. **Measured.**

| Run | Nodes (H100) | Flags | Final MFU | Mean MFU | tok/s | s/step |
|---|---|---|---|---|---|---|
| May402 | 2 (16) | none | 20.63 | **15.54** | 190,767 | 1.374 |
| May405 | 2 (16) | PGLE, no O1 | **21.30** | 15.03 | 197,012 | 1.331 |
| May403 | 4 (32) | none | 19.93 | 14.90 | 368,619 | 1.422 |
| May406 | 4 (32) | PGLE, no O1 | 20.12 | 14.30 | **372,090** | 1.409 |
| May404 | 2 (16) | O1/toolbox | 18.36 | 13.78 | 169,761 | 1.544 |

Reading these honestly:

- **~19.9% is the number the team quoted itself** ("~19.9 MFU on 4 nodes w/ SGD/Adam"), and it is a **final-step** figure — **mean MFU was 14.90**. Quoting 19.9 as sustained overstates it.
- The 21.30 peak is discounted by its own author: "PGLE without O1 is only marginal… Both PGLE runs warned `PGLE collected an empty trace`, so I would not treat these as a healthy PGLE success yet." The recommendation was "Use no-flags B4/device + `recompute_all` as the stable baseline."
- **Single-node full-shape reference: ~16 MFU** — "the best single-node SGD profile is still only around `16 MFU`" ([c/4760390864](https://github.com/marin-community/marin/issues/4312#issuecomment-4760390864)). Swapping XLA CE for Pallas CE moved it 16.07 → 19.00.
- **N4 did not scale.** "N4 roughly doubles tokens/sec versus N2 but MFU is flat/slightly lower."
- **>20% at 128 GPUs was never measured.** [#6693](https://github.com/marin-community/marin/issues/6693)'s top-level target — "> 20 MFU at 128 GPU scale in the production-relevant Grug MoE path" — has no result row; child [#6698](https://github.com/marin-community/marin/issues/6698)'s DoD ("A measured run is produced at 128 GPUs with full config") never closed. MAY-060 launched on 128 H100 on June 16 with **no result comment ever posted**.
- **#6367's own final self-assessment is bleaker than any table above:** its "best clean 8-node no-tensor-parallel smoke [was] still at ~1.8 MFU," and the issue was "effectively handed off to the pipeline-parallel path in #7024" ([Jul 6–12 summary](https://mws.oa.dev/summaries/summary-2026-07-06_2026-07-12.html)).

**Do not confuse these with two adjacent numbers.** The **90B-total / 5.3B-active** MoE on 256 H100 was driven 2.8% → **9.37%** MFU and declared "the practical pure-FSDP ceiling" ([#4302 c/4727421242](https://github.com/marin-community/marin/issues/4302#issuecomment-4727421242)) — a *different, larger-active* shape. And the widely-cited **~23.8% MFU** belongs to the **11B-A1.5B d2048 / 24-layer / 64-expert** validation model on 64×H100 under [#6716](https://github.com/marin-community/marin/issues/6716) — a much smaller model, and the summary itself flags the figure as optimistic because "the FLOP counter treats attention as fully quadratic and ignores the 2048-token sliding window."

## What happened instead: TPU

The run went to **v4-2048 (1,024 chips), us-central2, production priority** ([#6044 c/4820179240](https://github.com/marin-community/marin/issues/6044#issuecomment-4820179240)). Notably, **TPU did not rescue the run on MFU** — it rescued it on wall-clock. v4-1024 measured **21.54% MFU** at 1.49M tok/s but projected a **78.4-day** 10T runtime; the team "chose the larger v4-2048 for absolute throughput, accepting lower per-chip MFU (~13–18.6% versus ~21.5% on v4-1024) to cut projected wall-clock" to ~45–49 days.

The d2560 shape fit 1,024 chips badly for the same divisibility reason that surfaced a genuine silent-correctness bug: "the sharded NS calc in Muon was silently dropping when num_matrices didn't evenly divide into num_chips… written on v4-1024 where 256*26 is divisible by 512 chips. However it isn't divisible by 1024 chips."

As of the freshest data in this corpus (week of Jul 6–12): the run is **holding ~18.6% MFU on TPU v4-2048**, has passed **~2.1–2.3T of 10.07T tokens**, and full completion is **targeted** (not achieved) for around **August 30**.

## Postscript: Hopper came back in July

Two July developments reopened the H100 story, both reported **only in the [Jul 6–12 weekly summary](https://mws.oa.dev/summaries/summary-2026-07-06_2026-07-12.html)** — the corpus's GitHub slice ends ~July 4, so #6979, #6998 and #7024 have **zero primary chunks** and none of these numbers could be verified against a source comment:

- **JaxPP pipeline parallelism (#7024)** across four 8×H100 nodes on RNO2A reached **mean MFU 18.26 at ~414k tok/s** (explicit `std_1f1b`, batch 8192 / 256 microbatches, four six-layer stages) — "about 1.74 points below the 20 bar," after a week of gated negative results (pure-XLA ring combine −52%, input-gradient-first backward split −29%). David Hall told the GPU channel this meant "Hopper is back on the menu."
- **Larry Dial's GPU MFU Learning Path (#6979)** rebuilt the Hopper story from scratch and reported `model.py` weak-scaling "essentially flat from 1 to 8 nodes — 26.7% at 8 GPUs to 26.5% at 64 H100s" with replica/DDP, "whereas sharding the model across nodes costs about 4 points." This reframes the whole bring-up: the 20% bar looks clearable, and the production Levanter/grug stack — not Hopper — was the obstacle. **Treat with care:** the same thread's H100 "working copy" drops total experts 256→64 so the model fits one node, so this is likely *not* the 256-expert production config.

## Gaps and disagreements

- **The 18.26 and 26.5/26.7 figures are summary-only.** No primary source in this corpus. A related Discord message describes Larry's thread as an **H200** thread, while the summary says H100 — unresolved.
- **MAY-060 (128 H100) has no reported outcome**, so the single most relevant at-scale datapoint simply does not exist.
- **No H100 run ever used production seq8192**; all d2560 H100 work is seq4096. Any H100-vs-TPU MFU comparison is therefore not apples-to-apples.
- **No same-shape PP-vs-FSDP A/B on H100 exists.** "PP never beat FSDP" is safe as *never beat it head-to-head*; July's 18.26 mean MFU does exceed June's best 4-node FSDP mean of 14.90, but at a different shape and batch.
