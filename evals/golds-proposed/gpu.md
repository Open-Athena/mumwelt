# How training on GPUs is going

**Short version (frozen corpus, freeze date 2026-07-16).** GPU training is a central, actively-staffed workstream — the whole rest of the 2026 plan (an end-of-month B200 hero run, then the year's biggest run on the full 800+ B200 cluster) is meant to run on NVIDIA hardware, and July is explicitly a *preparation* month. But the honest state at the freeze is **"still fighting crashes and still under the MFU bar on both Hopper and Blackwell," not "about to land."** The two things a reader should not miss: (1) the weekly-summary narrative that the flagship 11B H100 validation run is "healthy… completion expected ~July 13–14" is **contradicted by the W&B ground truth in the same corpus** — every named MLA-500B run of that model on the freeze boundary is crashed or merely *running* mid-recovery, none finished; and (2) the sharpest, best-documented GPU-MFU result in the corpus is a **miss**: issue [#6304](https://github.com/marin-community/marin/issues/6304) targeted 25% MFU on the 90B-5.3BA MoE and closed out at **9.37%**, declaring ~9.4% "the practical pure-FSDP ceiling." Pipeline parallelism is the named fix, but the corpus-verifiable PP work is on TPU and was *parked*.

Hardware split kept throughout: **H100 = Hopper**, **B200 / GB200 = Blackwell / NVL72**. Numbers are labeled **achieved / target / projected / summary-asserted**, and every metric carries its hardware/config, because these are not interchangeable.

## 1. H100 (Hopper): the flagship 500B run — summary optimism vs. the crash wall

### 1a. What the weekly summary claims (summary-asserted, NOT run-logged)
The [2026-07-06→07-12 weekly summary](https://mws.oa.dev/summaries/summary-2026-07-06_2026-07-12.html) says the "compute-optimal Marin 11B-A1.5B validation run on H100 cleared **~23.8% MFU**… (~1.37M tokens/s, ~1.53 s/step at batch 512 × seq 4096)," on **64×H100**, "still running as of this writing (~264B tokens in), with completion expected around July 13–14," framed by Isaac Hodes as *"more about exercising the hardware instead of delivering an artifact"* (it is pushed to 500B tokens, past compute-optimal, to shake out the stack for the Blackwell path). The epic is [#6716](https://github.com/marin-community/marin/issues/6716) ("[Hero run] Land 8B-A1B XT on H100s," body: *"POC for multinode GPU run"* — no close-out comment exists in the corpus, and note the epic title says **8B-A1B**, smaller than the ~11B model actually run).

**Provenance caveat (load-bearing):** the **23.8% MFU / 1.37M tok/s / 1.53 s/step / "64×H100"** figures appear **only in that weekly-summary narrative**. Literal search of the frozen corpus returns **no W&B run** and **no issue/Discord** asserting them. The run cards for this model family log only `train/loss`, `eval/bpb`, `eval/loss`, `throughput/total_tokens`, `parameter_count`, `_step`, `_runtime` — **`throughput/mfu` and `tokens_per_second` are not captured for any d2048-500B run.** So 23.8% cannot be pinned to a logged run value and must be treated as **summary-asserted, not measured**. (1.37M tok/s is internally consistent with 512×4096 ÷ 1.53 s = 1.37M, i.e. an instantaneous steady-state derivation — but wall-clock throughput of the actual running jobs is ~560–590K tok/s, less than half.)

| `-r2-nosim-2node-20260713-234514` | **crashed** | — | — | died before 1st step |

Reads: **five crashed attempts fired inside a ~47-minute window the evening of 07-13** (the signature of a bring-up crash loop sweeping node-count × batch-size), the two that logged anything died at fresh-init loss ≈11.5. Recovery launched minutes later (07-14 00:18Z) into **three still-`running` attempts at only ~24–31% of 500B** — losses healthy (~1.7 and falling) but the *end-state at freeze is "in progress," and none is `state=finished`.* **There is no finished MLA-500B run anywhere in the corpus.** The still-tuning suffixes (`qkvscale`, `noswa` = no sliding-window attention) show the recipe was not even fixed yet. (Run URLs share the `https://wandb.ai/marin-community/marin_moe/runs/` prefix + the name above.)

### 1c. What actually *did* land (the likely source of the summary's optimism): the **gqa4** sibling
The one **finished** 500B H100 run in the corpus is a **different architecture**: [`grug-d2048-L24-gqa4-500B-r8-nosim-v2-20260709-042053`](https://wandb.ai/marin-community/marin_moe/runs/grug-d2048-L24-gqa4-500B-r8-nosim-v2-20260709-042053) — **state=finished**, GQA-4 (not MLA), `parameter_count = 1.077e10` (**10.77B**, ≠ the 11.05B MLA), **throughput/total_tokens = 5e11 (500B landed)**, final **train/loss 1.629, eval/bpb 0.7273, eval/loss 2.166**, tags `cw datakit grug h100 moe`. Its own same-day first attempt `-r8-20260709-031827` crashed first. This July-9 gqa4/10.77B/`r8` run is almost certainly what "a 64×H100 500B run cleared ~23.8% MFU" points to — but **(i)** it is the gqa4 model, not the 11B MLA model the summary/draft attribute a July-13–14 completion to, and **(ii)** even for it, **no MFU is logged in the frozen card** (only loss/bpb/tokens). The run name carries `r8` (8 replicas); the frozen card is truncated and does **not** expose `num_hosts`/`num_devices`, so even the "64×H100" count is summary-asserted, not read from the run.

**Reconciliation (the guard the draft missed):** the summary conflates a *finished gqa4/10.77B* run with a *crash-looping-then-recovering MLA/11.05B* run. At the 2026-07-16 freeze the true picture is: gqa4-500B landed on 07-09 (loss 1.629, no MFU logged); the MLA-500B run the "completion ~July 13–14" line describes was **crashed ×5 on 07-13 and only ~24–31% done and still running on 07-14** — "still fighting crashes," not "about to finish."

### 1d. The one rigorously-documented H100 MoE-MFU result is a **miss**: [#6304](https://github.com/marin-community/marin/issues/6304) — 25% target → 9.37% ceiling
This is the concrete origin of the whole "pipeline parallelism is the fix" narrative and the clearest target-vs-achieved gap in the GPU story (the draft omitted it entirely). Issue **[#6304](https://github.com/marin-community/marin/issues/6304)** "[grug] Drive 90B-5.3BA MoE MFU on cw-us-east-02a from 3% to ~25%" (rjpower), on the **90B-total / 5.3B-active** Grug MoE, **256 H100 / 32 nodes**, cluster **cw-us-east-02a** (CoreWeave), inherited from the bring-up [#6292](https://github.com/marin-community/marin/issues/6292) / PR [#6293](https://github.com/marin-community/marin/pull/6293) ("scale to 256 H100 + FSDP/EP sparse MoE").

- **Target:** ≥25% active-FLOPs MFU (≈2.0M tok/s). **Achieved (close-out):** *"2.8% → 9.37% MFU (3.3×) — batch 1024 × seq 2048 + `save_moe`, 712K tok/s… ~9.4% is the practical pure-FSDP ceiling for this 90B/5.3BA model on 256 H100 (comm-bound on latency-bound FSDP all-gathers, memory-capped at the optimal batch)."* → **target missed by ~2.7×.**
- Experiment ledger (all 256 H100, seq 2048): baseline batch 256 = **2.8%** / 221K tok/s → batch 512 = **5.37%** / 408K (+85%, near-linear) → batch 1024 = **9.32%** / 709K → +`save_moe` remat = **9.37%** / 712K (best). Batch 1536 and 2048 both **OOM**; PGLE OOM; XLA collective-combine flags **−7%**; pure-bf16 params → deterministic gang hang; the embed-backward reshard fix (`451ba5108b`) was **reverted** (−11% at batch 512 / OOM at 1024); microbatching *lowers* MFU (7.18%) because FSDP re-gathers params every microbatch.
- **Why it's a ceiling, not a stopping point:** profiling shows the step is **~82% communication** (batch-1024 profile), dominated by hundreds of small, latency-bound per-tensor FSDP all-gathers, while the throughput-optimal batch already fills HBM — a double bind where every remaining FSDP lever either OOMs or (microbatching) adds gathers. The named escape is a **different parallelism**: [#6321](https://github.com/marin-community/marin/issues/6321) "Deeper MoE MFU levers beyond the pure-FSDP ceiling" ranks **pipeline/tensor parallelism** as the highest-ceiling successor ("reduce gathers per token… hybrid FSDP is memory-blocked at 90B").

### 1e. Pipeline parallelism: verified on **TPU** and **parked**; the GPU-side realization is out-of-corpus
The corpus-verifiable PP work is [#6532](https://github.com/marin-community/marin/issues/6532) "Zero-bubble pipeline parallelism for Grug-MoE" (rjpower, PR [#6534](https://github.com/marin-community/marin/issues/6534)), and it is on **TPU v6e**, not H100: PP **beats FSDP at multi-host scale** — v6e-32 (8 hosts) **180,578 vs 148,221 tok/s (1.22× FSDP)** — but **loses on a single host (0.78×)**, because PP only wins once the FSDP all-gather has to cross the slow inter-host network. It was then **PARKED**: *"the PP / zero-bubble investigation for grug-MoE has been moved out of marin to rjpower/marin-experiments#11… PR #6534 is closed unmerged."* So PP validates the *principle* the #6304 diagnosis points to, but on different silicon and as a closed effort. **A separate GPU-side JaxPP effort and its "18.26% MFU" figure (issue #7024) are NOT in the frozen corpus** — there is **no in-corpus H100 PP MFU number** to close the loop against 9.37%. Treat any "Hopper is back on the menu / 18.26 MFU" claim as unverifiable here.

*(For scale reference, the only other logged H100 grug MFU data points are the June-9 cw-us-east-02a bring-up canaries in [#6292](https://github.com/marin-community/marin/issues/6292): d1024 on 64 H100 = 1.6M tok/s at ~5.4% MFU, an explicit 20-step liveness test — literally "exercising the hardware." No finished 64×H100 d2048-500B run with a logged MFU exists in the corpus.)*

## 2. B200 (Blackwell / NVL72): under the 20% gate, and the end-of-month run's size/rack is contested

### 2a. The gate: ≥20% MFU (achieved 17.8% is summary-asserted, below bar)
The end-of-month B200 run is **gated** on B200 MFU clearing 20%: [#6706](https://github.com/marin-community/marin/issues/6706) "Get B200 MFUs above X in advance of July run" (body: *"Need to be at 20%+?"*), tracked by [#6710](https://github.com/marin-community/marin/issues/6710) ("Training MFU % ≥20% per #6706; pushing toward the 25% target for September") and the 128-GPU workstream [#6693](https://github.com/marin-community/marin/issues/6693). The weekly summary reports **17.8% single-node on 8×B200** (via Tri Dao's QuACK/SonicMoE grouped GEMM wired into the expert MLPs; "width, not batch, is the live lever"), i.e. **below the ≥20% bar**. **Provenance caveat:** the 17.8% (and 14.9% / 12.5% / ~1,175 TFLOP/s) numbers live in **issue #7012, which is NOT in the frozen corpus** (only a Discord pointer to it exists) — so they are **summary-asserted, unverifiable against the freeze**. **20% is a bar and 25% is a September target — neither is an achieved result.**

### 2b. Freshest state at the freeze: a same-day (07-16→07-17) GB200 multi-rack bring-up that is *crashing above 128 GPU*
The freeze itself captures live GB200 activity the summary (which stops at 07-12) never covered — and it records **no MFU field for any GB200 run** (verified: 0 GB200 run cards contain `throughput/mfu`), so it updates the *narrative* without superseding 17.8%:

- **Attention-kernel sweep** `gb200-d1280-sonic-cute-{2..9}` (all **2026-07-16**, Larry Dial): varies `attention_implementation` ∈ {reference, cudnn, gpu_fa4_cute}. **`reference` (cute-2) and `cudnn` (cute-4) both failed; every 8.6B-param variant (cute-2/3/4/5/6) failed; only the smaller ~2.47B `gpu_fa4_cute` configs (cute-7/8/9) finished.** Purpose: pick the working Blackwell attention kernel; no throughput/MFU comparison logged.
- **d5120 / L48 (~129B-param) multi-rack scaling campaign** (07-16 into **07-17**): 32→64→128→256→512→640 GPU. `cudaasync` unblocked 64-GPU (`…64gpu-b1024-r2nons-cudaasync2`, `…r1/r2-muonh-cudaasync` all **finished**); **128-GPU / 2-rack** (`…128gpu-b2048-r2-intrarack`, `-intrarack-pad`) **finished** — the **largest stable/finished GB200 run at freeze** — while plain `-muonh` crashed; **256-GPU, 512-GPU, and 640-GPU all crashed** (512-GPU `-r8-segfix` was still `running` past midnight into 07-17). Derived throughput (not MFU, no FLOP baseline in corpus): ~463K tok/s at 128-GPU, ~250K at 64-GPU.

So the true Blackwell snapshot at freeze is: **single-node ~17.8% (summary-asserted, below the 20% bar) and an actively-crashing multi-rack bring-up above 128 GPU** — not a stable headline efficiency number.

### 2c. The end-of-month B200 hero run: size and rack count are **contested and undecided**
The draft (following the summary) called it "~120B-A8B on 2 NVL72." The tracking issue itself says otherwise. [#6689](https://github.com/marin-community/marin/issues/6689) "[Hero Run] nB-AmB XT on B200s" (owner @ClassicLarry) lists **"288 B200 (4×NVL72)"** and leaves **model size ("nB-AmB"), FLOP budget, tokens, WandB link, data mix, and pre-registered loss all blank/"?"**; its framing: *"the last run before we train on the full 800+ B200 cluster."* The weekly summary instead says **"~120B-A8B… on 2×NVL72."** These **conflict on two axes** — **rack/chip count (288 B200 / 4×NVL72 vs 2×NVL72 ≈ half)** and **model size (placeholder vs ~120B-A8B)** — and no in-corpus artifact reconciles them. Every substantive parameter is an open stub: architecture [#6701](https://github.com/marin-community/marin/issues/6701), data mix [#6700](https://github.com/marin-community/marin/issues/6700), pre-registered loss [#6702](https://github.com/marin-community/marin/issues/6702). **Bottom line: the run had NOT launched at freeze** (its ≥20% MFU gate is unmet at 17.8%, and size/data/loss are undecided). Report size and rack count as **contested**, not fact. *(The related commitment/cost issues the summary cites — #7073, #7074 — are not in the frozen corpus.)*

## 3. The other hero runs are still on **TPU** (attribution correction)
Only **one** in-flight hero *pretraining* run is clearly identifiable in the corpus, and it is on TPU: the **67B-A2B MoE (d2560) on 10T tokens** — [#6044](https://github.com/marin-community/marin/issues/6044) (tracking [#6704](https://github.com/marin-community/marin/issues/6704), "should likely land in August"). ClassicLarry: *"We have started the run on TPUs this morning **(v4-1024)**,"* but that initial **v4-1024** (512 chips) attempt **crashed at step 4367 and was superseded** — the team "doubled compute to **v4-2048** (all reserved nodes)." The **hero run runs on v4-2048 (1,024 chips)**, us-central2: run_id `moe_67b_a2b_d2560_ep1_rep16_bs4096_seq8192_sw2k_v4_2048_muon_10T`, resumed as `..._resume15k_v2_10T` (**state=running, ~3.2T of 10T tokens** at the 2026-07-16 freeze). Its winning v4-2048 config (EP=1, replica=8, BS=8192) sustains **~2.57M tok/s at 18.62% MFU** (~45-day projected 10T runtime); the higher **~1,485,929 tok/s / 21.5% MFU** figure is the **superseded v4-1024 attempt** (best *per-chip* MFU but ~78-day wall-clock). The `..._v4_2048_test` runs are config-sweep smoke tests that coexist with — but are not — the hero run. The draft's claim of "two" in-flight TPU hero pretraining runs is **not corroborated** — only the 67B-A2B is named.

## 4. Bottom line (labeled)
- **Working:** a real 500B-token run *did* land on H100 — the **gqa4 / 10.77B** run (`…gqa4-500B-r8-nosim-v2`, finished 07-09, loss 1.629, eval/bpb 0.727), though **its MFU is not logged in the corpus**; the #6304 campaign lifted 90B-5.3BA MoE MFU **3.3× (2.8%→9.37% achieved)**; the cw-us-east-02a 256-H100 cluster and GB200 racks are up and being driven; `cudaasync`/`intrarack-pad` unblocked GB200 up to 128 GPU.
- **Below target / still fighting:** the **11B MLA 500B run was crashed ×5 (07-13) and only ~24–31% done and running (07-14) at freeze — not finished**, contradicting the "completion ~July 13–14" narrative; H100 MoE MFU tops out at **9.37% (achieved) vs a 25% target (miss)** on the 90B model, pure-FSDP-ceiling-bound; **B200 ~17.8% (summary-asserted) < the 20% gate**; GB200 multi-rack is **crashing above 128 GPU** at freeze; **25% is a September target, not a result.** Pipeline parallelism is the named structural fix, but the only corpus-verifiable PP work is TPU-only and **parked** (#6532 → rjpower/marin-experiments#11); the GPU-side PP/JaxPP number is not in the corpus.
- **Undecided / on TPU:** the end-of-month **B200 hero run's size and rack count are contested** (#6689's *288 B200 / 4×NVL72, size "?"* vs the summary's *~120B-A8B / 2×NVL72*) and it **had not launched** (gate unmet, arch/data/loss open: #6700/#6701/#6702); the identifiable in-flight hero *pretraining* run remains on TPU (**67B-A2B on v4-2048**, ~18.62% MFU sustained, landing ~August).

### H100 optimizer close-out — Muon → SGD/Adam

The best **production-shape** H100 result in the corpus is **~19.9% MFU on 32 H100 (4 nodes) with SGD/Adam** — dlwh, 2026-06-26 (`#gpu`): *"~19.9 MFU on 4 nodes w/ SGD/Adam … Muon needs to go for now … we'll need much faster interconnect or PP"* — tracked under [#6693](https://github.com/marin-community/marin/issues/6693) (*">20 MFU at 128 GPUs workstream"*). This is why the production H100 path runs **SGD/Adam, not Muon**: on a single-node 8×H100 d2560 ring-MoE A/B ([#6493](https://github.com/marin-community/marin/issues/6493)), SGD held **16.19% MFU** (74,848 tok/s, 0.438 s/step) vs MuonH's **4.75%** (21,962 tok/s, 1.49 s/step) — Muon consumed ~500 ms of a ~1500 ms step. Caveats: substitute optimizer, **32 GPU not 128**, still **below the >20%@128-GPU bar**. Achieved-MFU ladder: 5.4% canary → 9.37% (90B pure-FSDP) → **19.9% (SGD/Adam, 32-GPU)**.
